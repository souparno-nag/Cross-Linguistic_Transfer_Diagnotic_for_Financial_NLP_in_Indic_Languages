# Digit-system audit — why the orthographic/numeral module is excluded

Evidence for CLAUDE4.md "Scope decisions". Generated by `python -m scripts.digit_audit`
(read-only, deterministic); the raw output is reproduced below.

## Finding

1. **Hindi and Telugu natives use ASCII digits only.** Bengali natives do not: in task 2,
   828 of 847 digit-bearing rows use Bengali digits only, 10 ASCII only, 9 mixed
   (task 3: 96 / 88 / 3 of 187).
2. **MT output is ASCII in every target language.** `ben→hin/tel/mal` therefore changes digit
   system on 810–822 of 847 digit-bearing rows (task 2); `hin→ben` stays ASCII.
   Consequence for T-113: native Bengali (Bengali digits) and MT Bengali (ASCII) differ
   in digit system as well as provenance.
3. **Mismatched items do not fail more often than matched ones.** Share of failure rows
   with a changed digit system vs share of *all* items in the same pair that changed:
   e.g. task 2 IndicBERT `ben→hin` 32.0% vs 34.2%, `hin→ben` 29.2% vs 34.2%; task 3
   17.8% vs 18.6%, `tel→ben` 14.0% vs 18.2%. At or below base rate throughout.
4. Overall 12.2% / 13.4% (task 2) and 7.9% / 10.6% (task 3) of failures (IndicBERT / mBERT)
   coincide with a digit-system change — the share a module at precedence rung 3 would
   have labelled.

## Why the module stays out

- **Spurious attribution.** The mismatch is present at the base rate among items that
  do *not* fail, so a label `orthographic_numeral_mismatch` on 8–13% of failures would
  be a correlate, not a cause. CLAUDE4.md hard rule 3 / working agreement: no
  attribution the data does not support.
- **Narrow reach.** Only Bengali-sourced or Bengali-native-evaluated conditions have any
  mismatch; Hindi↔Telugu conditions have none (counts of 0 above), so the module would be
  a no-op for most of the grid.
- **Currency is not measured.** An earlier substring-based currency count fired inside
  ordinary words and was discarded; no reliable currency signal exists here.
- **Task 1** (the numeral task) is out of scope for this build, and was verified by the
  maintainer to carry ASCII numerals in all its MT versions (not re-measured here).
- **Limits of this evidence:** the comparison is between the training-side text and the
  failing evaluation text. It shows no over-representation, not that the model is
  insensitive to digit script — that needs a controlled test. Dropped numbers
  (185 of 19,614 task-2 MT rows) are a separate effect (numeral loss, T-105), not an
  orthographic one.

If this is revisited, the cheaper option is an audit-trail covariate (no label, no
precedence slot) rather than restoring the module.
